# KCD2 Dual Subtitles — v0.3.3 maintenance handoff

_Updated 2026-08-25. This document supersedes the current-architecture guidance in the v0.3.2-era [`v0.3-development-handoff.md`](v0.3-development-handoff.md) where the two conflict. The older document remains the detailed source for the stable HUD/AVM1 retail evidence and RC history._

## 1. Scope

v0.3.3 is a maintenance/hardening release for the stable **generation-time fixed-pair** v0.3 product. It does not introduce runtime language switching, a new subtitle rendering transform, Menu.gfx integration or new KCD2 content formats.

It carries two sets of changes after v0.3.2:

- best-effort Windows autodetection for Steam, Epic Games Store and GOG/Galaxy, while preserving the existing Microsoft GDK/Xbox discovery and the store-neutral structural validation contract;
- crash-safe generation/publication recovery after a retail-observed stale duplicate mod caused by installer staging inside KCD2's scanned mod root.

## 2. Retail root cause for the v0.3.2 stale-style failure

The reported failure showed bilingual text but no requested presentation and no language tags. Changing the selected Secondary language and regenerating also failed to change the in-game second language.

The exact reported English + Czech generator configuration was separately proved to generate:

```text
[EN] Primary<br/><font color='#FF8080' size='24'>[CS] Vedlejší</font>
```

and a derived HUD Data PAK. Therefore the generator-owned localization/presentation bytes were not the missing layer.

Retail `Documents\kcd.log` identified the actual activation problem: v0.3.2 could leave a directory such as:

```text
.kcd_dual_subtitles.staging-3747685633
```

as a direct child of the resolved KCD2 mod root. KCD2 scans direct child directories as candidate mods. The log showed both that stale staging copy and the canonical `kcd_dual_subtitles` directory discovered, with the leaked staging copy used for localization/Data PAK loading.

That explains the complete observed pattern without changing the retail-proven direct-HTML Scaleform transform. The transform remains unchanged in v0.3.3.

The old native GUI also executed the complete Generate/Regenerate synchronously in the Win32 command handler. A legitimate long operation could make the window appear frozen; terminating it then skipped deferred cleanup. This is a credible mechanism for the leaked staging directory, but it is not evidence that the generator core deadlocked.

## 3. Current publication invariant

**Never create a directory-shaped generation/install workspace inside the resolved KCD2 mod root.**

For an automatic install targeting:

```text
<ModsRoot>\kcd_dual_subtitles
```

v0.3.3 creates a same-volume sibling transaction directory beside `ModsRoot`:

```text
<parent-of-ModsRoot>\.kcd2-dual-subtitles-install-*
```

The transaction owns:

- `staged` — the newly generated candidate;
- `previous` — the previous canonical installation when one existed;
- `mod_order.next` / `mod_order.previous` when load-order publication changes;
- atomic state markers for `building`, `publishing`, and `committed`;
- `had-previous`, persisted before an existing canonical installation is moved.

KCD2 never sees the transaction as a candidate mod because it is outside `ModsRoot`.

## 4. Transaction and recovery contract

The recovery state is monotonic and crash-aware.

### Building

The canonical installation has not been replaced. An interrupted building transaction is discarded without touching the existing target.

### Publishing

The transaction may own the only previous complete installation and the canonical target may be absent, partially copied or already replaced.

Recovery:

- restores `previous` when present;
- restores the old `mod_order.txt` when the transaction had replaced it;
- removes an uncommitted fresh target only when the transaction proves there was no previous installation;
- preserves the transaction workspace when rollback is blocked by a transient filesystem failure so a later run can retry safely.

### Committed

The verified canonical target and committed load-order state are authoritative. Recovery keeps them and cleans only transaction residue.

Committed cleanup removes the committed marker last. If termination happens after that final marker is removed but before the empty transaction directory itself is removed, the markerless residue is cleaned conservatively without modifying the canonical target.

### Completed rollback cleanup

`had-previous` distinguishes a successful rollback whose `previous` directory has already been renamed back to the canonical target from a failed fresh install. If the process terminates while cleaning that transaction residue, recovery keeps the restored canonical installation.

## 5. Legacy v0.3.2 recovery

Before a new publication, the installer inspects tool-owned legacy residue from v0.3.2 and earlier.

For `.kcd_dual_subtitles.staging-*` directories:

- a unique `.previous` backup is restored rather than deleted blindly;
- multiple previous-install backups are treated as ambiguous and fail closed;
- stale staging residue is removed after safe recovery.

For old `mod_order.txt` transaction files:

- a unique previous file is restored when the canonical `mod_order.txt` is missing;
- temporary/obsolete residue is removed when the canonical load order is already present;
- ambiguous previous files fail closed.

This migration exists specifically so upgrading from an interrupted v0.3.2 Regenerate cannot discard the only previous complete installation.

## 6. Artifact-integrity contract

Generation success now requires the produced artifact to match the exact deterministic request.

Verification covers:

- `mod.manifest` contents/version;
- every expected generated localization PAK and no unexpected localization files;
- exact derived HUD Data PAK in styled mode;
- absence of a HUD Data PAK in localization-only mode;
- no symlinks, non-regular files, duplicate entries or unexpected files.

The check runs for:

1. portable ZIP bytes before the ZIP is published;
2. the staged automatic-install directory after generation;
3. the final canonical directory after rename or guarded copy publication.

A corrupt guarded-copy result is rejected and the previous installation is rolled back.

This proves the filesystem artifact that the application reports as installed. It does not by itself prove what a running KCD2 process has already loaded into memory, so the GUI explicitly requires a game restart before testing a regenerated result.

## 7. `mod_order.txt` ownership

When an existing `mod_order.txt` needs the project entry added, its change is part of the same install transaction as the mod directory.

The previous file is retained until commit. A failed publication or interrupted publishing state restores both the mod directory and the old load-order file together.

The application still does not create `mod_order.txt` when it is absent.

## 8. Cross-process operation lock

Windows Generate/Regenerate/Uninstall mutations are serialized with a file lock on a persistent sibling file:

```text
.kcd2-dual-subtitles-operation.lock
```

The named lock file is intentionally kept after unlock. Deleting it would introduce an unlink/recreate race where another process could already hold the old file while a third process creates and locks a new independent file.

The lock file is outside KCD2's scanned mod root.

## 9. GUI generation behavior

Generate/Regenerate runs on a background goroutine rather than the Win32 command handler.

While generation is active:

- the window remains responsive;
- game root, `Browse...`, language controls and presentation controls stay disabled so the UI/service selection cannot drift away from the captured generation request;
- the user is warned before closing the window;
- the filesystem transaction remains the recovery authority if the process is nevertheless terminated.

On success the GUI reports whether a styled HUD or localization-only patch was installed, shows the resolved install path and tells the user to restart KCD2 before testing.

## 10. Uninstall relationship to generation recovery

Uninstall acquires the same operation lock and first recovers an interrupted Generate/Regenerate transaction. This prevents an old installation parked in a pending transaction from being restored after the user explicitly uninstalls the canonical mod.

The uninstall directory backup is also kept outside the scanned KCD2 mod root, so an interrupted uninstall cannot leave a second loadable copy of the mod there.

v0.3.3 does not claim that every individual step of Uninstall itself is a durable multi-resource crash transaction. Its required guarantee for this maintenance fix is that generation recovery is resolved first and no directory-shaped uninstall backup becomes another KCD2 mod candidate.

## 11. Store-neutral autodetection after v0.3.2

Best-effort Windows discovery now combines:

- existing Microsoft GDK/Xbox `.GamingRoot` / `XboxGames` sources;
- Steam install roots and `libraryfolders.vdf`, including custom libraries;
- Epic launcher `.item` manifests under ProgramData;
- GOG installed-game registry entries, Galaxy library metadata and conventional GOG library roots.

Launcher metadata only yields candidate paths. Every candidate must still pass existing `NormalizeSelection` / structural KCD2 validation. Store identity never selects a different generator, localization format, HUD transform or install-content contract.

Malformed or missing metadata for one launcher fails soft and does not suppress valid candidates from other sources. Manual `Browse...` remains authoritative.

## 12. Stable HUD transform remains unchanged

The accepted v0.3 HUD architecture remains:

- derive `Libs/UI/hud.gfx` from the user's installed game;
- patch standard bottom subtitles and overhead bubbles using semantic AVM1 anchors;
- restore generated `htmlText` after vanilla sizing/processing;
- apply optional outline/shadow TextField properties when requested;
- package the derived HUD in `Data/kcd_dual_subtitles.pak` using the existing CryPak-compatible writer;
- fail closed on unknown foreign HUD overrides in the same resolved mod root.

Do not rewrite the direct-HTML transform to address the v0.3.2 stale-style incident. Retail evidence identified publication/duplicate-mod activation as the cause.

Narrative `fc_setNarrativeSubtitles` support remains separate future work under #54. Runtime language switching remains future work under #39.

Automated coverage includes:

- missing/corrupt generated artifact rejection;
- unexpected HUD rejection in localization-only mode;
- corrupt guarded-copy publication rollback;
- staging/transaction workspace outside the scanned mod root;
- legacy leaked staging recovery/cleanup;
- legacy load-order recovery;
- interrupted replacement, fresh publication, build and committed cleanup states;
- completed rollback cleanup with `had-previous`;
- markerless final committed-cleanup residue preserving the published target;
- retryable failed rollback retaining recovery state;
- Windows cross-process lock behavior;
- Uninstall recovering pending generation state and using an external directory backup;
- native GUI/CLI Windows smoke coverage through CI.
