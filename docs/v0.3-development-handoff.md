# KCD2 Dual Subtitles — v0.3 engineering handoff

_Last updated for the stable v0.3.0 release preparation on 2026-08-24._

This document preserves the technical evidence and constraints that are useful for future work after v0.3.0. Public usage belongs in [`README.md`](../README.md); release scope belongs in [`ROADMAP.md`](../ROADMAP.md).

## 1. Stable v0.3 product contract

v0.3.0 is a **generation-time fixed-pair bilingual subtitle tool**.

The user selects Main and Secondary source languages in the Windows GUI. The generator reads those installed localization PAKs, builds changed dialogue rows, and publishes the same generated patch under every supported localization PAK present in the selected installation. Consequently, the selected bilingual pair is independent of KCD2's currently active text language.

This architecture is deliberately different from the larger runtime-switching system originally planned in #39. Stable v0.3.0 does **not** provide an in-game language switch or Menu.gfx settings page.

## 2. Project rules to preserve

- Keep `main` releasable; production work goes through branches and PRs.
- GitHub Actions is the automated acceptance source.
- Do not commit or redistribute proprietary KCD2 localization or GFX files.
- Real retail assets may be inspected privately only for compatibility evidence.
- Never modify original KCD2 files.
- Unknown/malformed GFX or PAK structure must fail closed.
- Do not silently compose with an unknown third-party HUD replacement.
- Prefer narrow semantic transformations over absolute offsets or broad binary rewrites.
- Keep the application dependency-light and one-executable GUI/CLI architecture.
- Do not call CI-only behavior retail-proven.

## 5. Why the generated patch targets every installed language slot

A v0.3 RC exposed a design bug when Czech was selected as Main and German as Secondary while the game itself remained English. The generator originally wrote only `Localization/Czech_xml.pak`; KCD2 continued loading its active English localization slot, so the mod appeared absent.

The corrected contract separates:

- **source languages** — the two localization tables used to construct bilingual text;
- **game-facing localization slots** — every supported localization PAK actually present in the installation.

The same generated patch payload is emitted under all discovered supported slots for both automatic installation and portable ZIP output.

Do not re-couple selected Main language to a single output PAK.

## 6. Retail HUD evidence

Validated retail GFX hashes from the original 1.5.6 investigation (do not commit the binaries):

- `hud.gfx`: SHA-256 `85303baaeaa925ae051fe49626f15e638642908599886168682a16e402a065cd`;
- `Menu.gfx`: SHA-256 `7f37d24fc14b3961fb58b403340532a947239a4a0bdce01f059485572d841c1c`.

Both are Scaleform CFX/SWF v8.

### Standard bottom subtitles

Retail entry point:

```text
fc_setSubtitles(text, speakerName, isPlayer)
```

Final field:

```text
bc.subtitles.inside.tField
```

Important: the function receives already-resolved text, not a localization row ID.

Vanilla sizing can overwrite inline font size if custom HTML is applied too early. The working patch therefore:

1. saves the original generated HTML;
2. lets the complete vanilla function run;
3. restores final `htmlText` after vanilla sizing;
4. reruns the existing position/background calls.

### Overhead NPC bubbles

Retail entry point:

```text
fc_setBubbleText(bubbleId, bubbleText, speakerName, playerDistance)
```

Effective field path:

```text
cccursor.bubbles[Enum.BUBBLE_NAME_CORE + bubbleId].inside.tfText
```

The accepted bubble patch uses the same post-vanilla HTML-restoration principle, then recalculates the bubble vertical geometry and background.

### Narrative/cinematic captions

Retail exposes a separate path:

```text
fc_setNarrativeSubtitles(text, layout, fadeIn)
fc_hideNarrativeSubtitles(fadeOut)
```

An opening cinematic caption remained outside the proven standard/bubble transformation while later subtitles in the same cutscene worked. The exact final narrative TextField/member path and its geometry/fade lifecycle remain unresolved under #54.

Do not reuse standard/bubble assumptions blindly. Narrative work is future scope and must be research-first.

## 7. Stable presentation model

The generator owns presentation. GUI code only maps control values into the generator configuration.

Stable controls include:

- optional primary color;
- optional primary size (`0`/blank means vanilla size);
- primary italic;
- secondary color;
- secondary size;
- secondary italic;
- language tags on/off;
- common outline on/off;
- common shadow on/off.

Secondary defaults remain the live-proven prototype values (`#7FDBFF`, size `24`, italic on). Primary color/size remain vanilla unless explicitly set.

Color input uses exact `#RRGGBB`; explicit size bounds are `12..48`. These bounds are an implementation safety range, not a claim that every value was separately retail-tested.

### Outline/shadow implementation

Scaleform exposes direct TextField extensions, so the v0.3 implementation uses TextField properties rather than building filter arrays.

Outline prototype:

```text
TextField.outline = 1
```

Shadow uses conservative fixed values:

- black;
- alpha 1;
- blur 2 × 2;
- angle 45;
- distance 1;
- quality 1;
- strength 1.

These effects apply to the complete bilingual TextField, not separate primary/secondary lines.

When both effects are disabled, generation deliberately routes through the already-proven direct-HTML patcher without readability-property writes.

## 8. Generated HUD/Data PAK architecture

Styled mode:

1. reads the user's current `Data/IPL_GameData.pak`;
2. extracts `Libs/UI/hud.gfx`;
3. applies deterministic semantic AVM1 transforms;
4. creates `Data/kcd_dual_subtitles.pak` containing the derived HUD;
5. builds localization patch PAKs for all installed supported localization slots;
6. installs the generated mod under Windows Documents.

No prebuilt KCD2 HUD is distributed.

### CryPak ZIP lesson

A ZIP that is valid to Go/7-Zip can still be rejected by KCD2 CryPak. The game-facing Data PAK writer intentionally uses compatible ZIP version/header fields and is covered by raw-byte tests.

Do not casually replace the Data PAK writer with ordinary `archive/zip` output without preserving the tested CryPak header contract.

## 9. Foreign HUD conflict policy

Styled mode supplies `Libs/UI/hud.gfx`.

The installer scans other installed mods for a foreign HUD supplied either loosely or through a Data PAK. If one is found, generation/install stops with an explicit conflict rather than silently changing precedence or attempting an unvalidated binary merge.

A future composition feature would need to identify the actual effective HUD and pass the same semantic validation before patching it.

## 10. Installation and OneDrive behavior

Automatic installation targets:

```text
<Documents>\kingdomcome_mods\kcd_dual_subtitles
```

The Windows Known Folders API is used, so redirected/OneDrive Documents are supported.

Normal publication prefers staged same-volume rename. A real OneDrive-backed failure showed that Windows can return permission/sharing errors for the final rename even when directory creation and writes succeed.

Current publication strategy:

1. retry retryable permission/sharing rename failures with bounded backoff;
2. if retries are exhausted, use a guarded recursive copy into an absent target;
3. reject symlinks, unexpected targets and non-regular staged files;
4. preserve the previous installation until the new target and load-order update succeed;
5. remove a partial target and restore the previous installation if publication fails.

The copy fallback is compatibility behavior for cloud-backed Documents, not the normal path.

## 11. AVM1 patching rules learned during v0.3

- Locate `DefineFunction2` targets structurally; never depend on one absolute offset.
- Parse nested `DefineFunction2`, `DefineFunction`, `With` and `Try` bodies when searching.
- Validate function parameters, register bindings and semantic string/member anchors before mutation.
- Preserve unrelated SWF tags/actions byte-for-byte where practical.
- Use explicit idempotence markers.
- Retail functions may contain guarded early `ActionReturn`; inspect branch targets rather than banning all early returns.
- Respect `DefineFunction2` register ownership and use only structurally spare persistent registers.
- Keep proof questions separate: localization transport, CryPak loading, HUD resource precedence, AVM1 execution, lookup and TextField presentation are independent failure gates.

## 12. Historical RC experiments worth remembering

| Experiment | Result | Lesson |
| --- | --- | --- |
| localization-only font/italic markup | no visible independent style | vanilla HUD processing can overwrite early formatting |
| hidden HTML-comment carrier | only primary visible | hidden carrier data is a poor diagnostic transport |
| visible sentinel carrier | sentinel visible | localization transport worked; downstream execution was the failing layer |
| first Data PAK attempts | ordinary ZIP readable but game rejected it | CryPak compatibility needs raw ZIP-header validation |
| direct HUD marker | marker visible | generated HUD won resource resolution and executed |
| complex inline carrier parser | no style | reduce proof complexity; mutate one known field first |
| first direct-HTML patch | failed on early return guard | inspect real AVM1 control flow before imposing invariants |
| post-vanilla direct HTML | bottom subtitles styled | restore `htmlText` after vanilla sizing |
| bubble transform | bottom + overhead styled | overhead path is separate |
| forced centering | dialogue choices displaced | do not impose alignment without a demonstrated need |
| centering removed | choices returned to normal alignment | keep localization HTML minimally invasive |

## 13. Architectural limitation of the fixed-pair v0.3 path

The generated HTML lives in dialogue localization rows. Those same rows can also be consumed by other UI surfaces such as dialogue choices.

This is acceptable for the stable v0.3 fixed-pair product after the forced-centering regression was removed, but it is not the right transport for a future runtime-language system.

A future runtime design should apply presentation inside the subtitle render paths rather than making all consumers of a dialogue localization row understand subtitle-specific markup.

## 14. Future runtime-language work — #39

#39 remains useful research, but it is no longer the definition of stable v0.3.0.

The next meaningful proof is still narrow:

1. generate a project-owned namespaced localization key;
2. resolve it in the retail HUD through `TextExtension.translateString`;
3. prove that a missing key falls back safely and never displays a raw project key.

Only after that retail proof should work proceed to:

- universal generated secondary-language data;
- runtime session state / Off;
- live secondary-language switching;
- Menu.gfx settings integration;
- persistence research.

Do not introduce KCSE, MCM, LuaDB, ASI or `dinput8.dll` into the Xbox-first baseline without an explicit architecture change.

## 15. Presentation preview

The preview proposed in #61 was intentionally deferred from stable v0.3.0.

A true retail-equivalent external preview would require a compatible Scaleform runtime and creates licensing/dependency problems. A future built-in preview should therefore be clearly approximate, render from the generator-owned presentation model, and never become a second formatting implementation.
