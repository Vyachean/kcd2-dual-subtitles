# KCD2 Dual Subtitles — v0.3 engineering handoff

_Last updated for the v0.3.2 maintenance release on 2026-08-24._

This document preserves the technical evidence and constraints useful for work after the stable v0.3 release line. Public usage belongs in [`README.md`](../README.md); release scope belongs in [`ROADMAP.md`](../ROADMAP.md).

## 1. Stable v0.3 product contract

The stable v0.3 line is a **generation-time fixed-pair bilingual subtitle tool**.

The user selects Main and Secondary source languages. The generator reads those installed localization PAKs, builds changed dialogue rows, and publishes the same generated patch under every supported localization PAK present in the selected installation. The bilingual pair is therefore independent of KCD2's currently active text language.

The compatibility contract is **store-neutral on Windows**. Store/launcher identity does not select a different generator. A compatible KCD2 root is validated structurally, and automatic installation resolves the required mod filesystem layout from the selected installation.

The v0.3 maintenance sequence is:

- `v0.3.0` — stable fixed-pair + styled HUD feature set;
- `v0.3.1` — removed accidental English/Russian and storefront assumptions from game-root validation;
- `v0.3.2` — makes install/status/uninstall use one layout-aware mod-root resolver instead of always using the Microsoft GDK Documents path.

The larger runtime-switching system in #39 remains future work. Stable v0.3 does **not** provide an in-game language switch or Menu.gfx settings page.

## 2. Project rules to preserve

- Keep `main` releasable; production work goes through branches and PRs.
- GitHub Actions is the automated acceptance source.
- Do not commit or redistribute proprietary KCD2 localization or GFX files.
- Real retail assets may be inspected privately only for compatibility evidence.
- Never modify original KCD2 files.
- Unknown/malformed GFX or PAK structure must fail closed.
- Do not silently compose with an unknown third-party HUD replacement.
- Prefer narrow semantic transformations over absolute offsets or broad binary rewrites.
- Keep the application dependency-light and one-executable GUI/CLI architecture.
- Do not call CI-only behavior retail-proven.
- Do not encode Steam/GOG/Epic/Xbox as generator modes. Store identity is not a content-format concern.
- Install, status, HUD-conflict scan, `mod_order.txt`, Regenerate and Uninstall must all use the **same resolved mod root for the currently selected game installation**.

## 5. Why the generated patch targets every installed language slot

A v0.3 RC exposed a design bug when Czech was selected as Main and German as Secondary while the game remained English. The generator originally wrote only `Localization/Czech_xml.pak`; KCD2 continued loading its active English localization slot, so the mod appeared absent.

The corrected contract separates:

- **source languages** — the two localization tables used to construct bilingual text;
- **game-facing localization slots** — every supported localization PAK actually present in the installation.

The same generated patch payload is emitted under all discovered supported slots for automatic installation and portable ZIP output.

Do not re-couple selected Main language to a single output PAK.

## 6. Retail HUD evidence

Validated retail GFX hashes from the original 1.5.6 investigation (do not commit the binaries):

- `hud.gfx`: SHA-256 `85303baaeaa925ae051fe49626f15e638642908599886168682a16e402a065cd`;
- `Menu.gfx`: SHA-256 `7f37d24fc14b3961fb58b403340532a947239a4a0bdce01f059485572d841c1c`.

Both are Scaleform CFX/SWF v8.

### Standard bottom subtitles

Retail entry point:

```text
fc_setSubtitles(text, speakerName, isPlayer)
```

Final field:

```text
bc.subtitles.inside.tField
```

The function receives already-resolved text, not a localization row ID.

Vanilla sizing can overwrite inline font size if custom HTML is applied too early. The working patch therefore saves generated HTML, lets the complete vanilla function run, restores final `htmlText` after vanilla sizing, then reruns the existing position/background calls.

### Overhead NPC bubbles

Retail entry point:

```text
fc_setBubbleText(bubbleId, bubbleText, speakerName, playerDistance)
```

Effective field path:

```text
cccursor.bubbles[Enum.BUBBLE_NAME_CORE + bubbleId].inside.tfText
```

The accepted bubble patch uses the same post-vanilla HTML-restoration principle, then recalculates required bubble vertical geometry/background.

### Narrative/cinematic captions

Retail exposes a separate path:

```text
fc_setNarrativeSubtitles(text, layout, fadeIn)
fc_hideNarrativeSubtitles(fadeOut)
```

An opening cinematic caption remained outside the proven standard/bubble transformation while later subtitles in the same cutscene worked. The exact final narrative TextField/member path and its geometry/fade lifecycle remain unresolved under #54.

Do not reuse standard/bubble assumptions blindly. Narrative work is future scope and must be research-first.

## 7. Stable presentation model

The generator owns presentation. GUI code only maps controls into the generator configuration.

Stable controls include:

- optional primary color;
- optional primary size (`0`/blank means vanilla size);
- primary italic;
- secondary color;
- secondary size;
- secondary italic;
- language tags on/off;
- common outline on/off;
- common shadow on/off.

Secondary defaults remain the accepted prototype values (`#7FDBFF`, size `24`, italic on). Primary color/size remain vanilla unless explicitly set.

Color input uses exact `#RRGGBB`; explicit size bounds are `12..48`. These are implementation safety bounds, not claims that every value was separately retail-tested.

### Outline/shadow implementation

Scaleform exposes direct TextField extensions, so v0.3 uses TextField properties rather than building filter arrays.

Outline:

```text
TextField.outline = 1
```

Shadow uses conservative fixed values:

- black;
- alpha 1;
- blur 2 × 2;
- angle 45;
- distance 1;
- quality 1;
- strength 1.

These effects apply to the complete bilingual TextField. When both effects are disabled, generation routes through the accepted direct-HTML patcher without readability-property writes.

## 8. Generated HUD/Data PAK architecture

Styled mode:

1. reads the user's current `Data/IPL_GameData.pak`;
2. extracts `Libs/UI/hud.gfx`;
3. applies deterministic semantic AVM1 transforms;
4. creates `Data/kcd_dual_subtitles.pak` containing the derived HUD;
5. builds localization patch PAKs for all installed supported localization slots;
6. resolves the selected installation's `ModsRoot` and publishes the project directory there.

No prebuilt KCD2 HUD is distributed.

### CryPak ZIP lesson

A ZIP that is valid to Go/7-Zip can still be rejected by KCD2 CryPak. The game-facing Data PAK writer intentionally uses compatible ZIP version/header fields and is covered by raw-byte tests.

Do not replace the Data PAK writer with ordinary `archive/zip` output without preserving the tested CryPak header contract.

## 9. Foreign HUD conflict policy

Styled mode supplies `Libs/UI/hud.gfx`.

The installer scans other mods **in the same resolved `ModsRoot` where it will publish** for a foreign HUD supplied either loosely or through a Data PAK. If one is found, generation/install stops rather than silently changing precedence or attempting an unvalidated binary merge.

A future composition feature would need to identify the actual effective HUD and pass the same semantic validation before patching it.

## 10. Install-location architecture (`v0.3.2`)

The v0.3.1 generator became store-neutral, but install/status/uninstall still called `documentsPath()` directly. That meant a manually selected Steam/GOG/Epic-style root could generate correctly yet publish into the Microsoft GDK Documents location. This was a real architecture inconsistency, not merely a documentation error.

`v0.3.2` introduces one filesystem-level resolver:

```text
modinstall.ResolveInstallLocation(gameRoot) -> InstallLocation{ModsRoot, Layout}
```

The resolver does **not** identify a storefront. It selects only the mod filesystem convention required by the selected installation:

### Normal PC layout

```text
<game-root>\Mods
```

### Microsoft GDK packaged layout

```text
<Documents>\kingdomcome_mods
```

GDK is recognized from package artifacts rather than library path names:

- `gamelaunchhelper.exe` in the selected root;
- `MicrosoftGame.config` in/adjacent to the selected root;
- `appxmanifest.xml` in/adjacent to the selected root.

Do not regress to `XboxGames` path matching. GDK libraries can be moved/customized, and the path name is not the relevant content contract.

The same resolved root is now passed to:

- publication/staging/rollback;
- foreign-HUD scan;
- `mod_order.txt` integration;
- installed status;
- Regenerate state;
- Uninstall.

`application.Service` keeps the normalized selected game root in shared pointer state. This matters because the native GUI stores/copies the service by value; copies must still refer to the same current selection. A unique autodetected root is remembered, and manual `ValidateGameRoot`/`Browse...` replaces it. `refreshLanguageControls` also refreshes install state for the newly selected root.

If no game root is selected, status/uninstall fail closed rather than inspecting an unrelated default path.

Automatic installation remains Windows-only. Portable ZIP behavior is unchanged on non-Windows builds.

## 11. Publication and OneDrive behavior

Publication is staged under the resolved `ModsRoot`, so same-volume replacement/rollback works identically for standard `<game-root>\Mods` and GDK Documents roots.

For GDK, Windows Known Folders resolves the real Documents path, including redirected/OneDrive Documents.

A real OneDrive-backed failure showed that Windows can return permission/sharing errors for the final rename even when directory creation and writes succeed. Current strategy:

1. retry retryable permission/sharing rename failures with bounded backoff;
2. if retries are exhausted, use a guarded recursive copy into an absent target;
3. reject symlinks, unexpected targets and non-regular staged files;
4. preserve the previous installation until the new target and load-order update succeed;
5. remove a partial target and restore the previous installation if publication fails.

The copy fallback is compatibility behavior, not the normal path.

## 12. AVM1 patching rules learned during v0.3

- Locate `DefineFunction2` targets structurally; never depend on one absolute offset.
- Parse nested `DefineFunction2`, `DefineFunction`, `With` and `Try` bodies when searching.
- Validate function parameters, register bindings and semantic string/member anchors before mutation.
- Preserve unrelated SWF tags/actions byte-for-byte where practical.
- Use explicit idempotence markers.
- Retail functions may contain guarded early `ActionReturn`; inspect branch targets rather than banning all early returns.
- Respect `DefineFunction2` register ownership and use only structurally spare persistent registers.
- Keep proof questions separate: localization transport, CryPak loading, HUD resource precedence, AVM1 execution, lookup and TextField presentation are independent failure gates.

## 13. Historical RC experiments worth remembering

| Experiment | Result | Lesson |
| --- | --- | --- |
| localization-only font/italic markup | no visible independent style | vanilla HUD processing can overwrite early formatting |
| hidden HTML-comment carrier | only primary visible | hidden carrier data is a poor diagnostic transport |
| visible sentinel carrier | sentinel visible | localization transport worked; downstream execution was the failing layer |
| first Data PAK attempts | ordinary ZIP readable but game rejected it | CryPak compatibility needs raw ZIP-header validation |
| direct HUD marker | marker visible | generated HUD won resource resolution and executed |
| complex inline carrier parser | no style | reduce proof complexity; mutate one known field first |
| first direct-HTML patch | failed on early return guard | inspect real AVM1 control flow before imposing invariants |
| post-vanilla direct HTML | bottom subtitles styled | restore `htmlText` after vanilla sizing |
| bubble transform | bottom + overhead styled | overhead path is separate |
| forced centering | dialogue choices displaced | do not impose alignment without demonstrated need |
| centering removed | choices returned to normal alignment | keep localization HTML minimally invasive |

## 14. Architectural limitation of the fixed-pair path

Generated HTML lives in dialogue localization rows. Those same rows can also be consumed by UI surfaces such as dialogue choices.

This is acceptable for the stable fixed-pair product after the forced-centering regression was removed, but it is not the right transport for a future runtime-language system.

A future runtime design should apply presentation inside subtitle render paths rather than making all consumers of a dialogue localization row understand subtitle-specific markup.

## 15. Future runtime-language work — #39

#39 is future work, not unfinished stable-v0.3 scope.

The next meaningful proof remains narrow:

1. generate a project-owned namespaced localization key;
2. resolve it in the retail HUD through `TextExtension.translateString`;
3. prove that a missing key falls back safely and never displays a raw project key.

Only after that retail proof should work proceed to universal generated secondary-language data, runtime state/Off, live switching, Menu.gfx integration and persistence research.

Do not introduce KCSE, MCM, LuaDB, ASI or `dinput8.dll` into the dependency-free Windows baseline without an explicit architecture change.

## 16. Presentation preview

The preview proposed in #61 was intentionally deferred; future tracking is #71.

A true retail-equivalent external preview would require a compatible Scaleform runtime and creates licensing/dependency problems. A future built-in preview should be clearly approximate, render from the generator-owned presentation model, and never become a second formatting implementation.
