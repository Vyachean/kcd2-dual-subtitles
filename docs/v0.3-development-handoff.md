# KCD2 Dual Subtitles — v0.3 development handoff

_Last updated: 2026-08-24. Repository baseline: `main` at `f681cb1563e29d406ff2d4bc07fa4fdb9b1b1328` after PR #59._

This document is the continuity source for future v0.3 development sessions. Read it together with active issues #39, #54, and #55 before changing the v0.3 path. It distinguishes retail-proven behavior from code that is only CI-accepted and records the failed experiments that must not be repeated without a new hypothesis.

## 1. Project rules that must be preserved

- Plan each implementation slice before changing production code.
- Keep `main` releasable; production changes go through a branch and PR.
- GitHub Actions is the only automated acceptance source. Local builds/tests may help editing/debugging but are not merge/release evidence.
- Prefer small coherent PRs and explicit retail gates over speculative rewrites.
- Keep the project dependency-light; use the Go standard library where practical.
- Keep one Windows executable; the native Win32 GUI and CLI share the same application/generator core.
- Never modify original game files.
- Never commit or redistribute proprietary KCD2 localization/GFX assets. Real game files may be inspected privately for compatibility evidence only; CI uses synthetic fixtures.
- Unknown or malformed game UI structures fail closed rather than producing a possibly broken HUD.
- Do not advise users to disable Defender/SmartScreen. The executable is unsigned; release artifacts are produced by GitHub Actions with checksums.
- Do not call a feature retail-accepted merely because CI is green.

## 4. Private retail GFX findings

Do not commit proprietary assets or derived full binaries.

Validated hashes:

- `hud.gfx`: SHA-256 `85303baaeaa925ae051fe49626f15e638642908599886168682a16e402a065cd`;
- `Menu.gfx`: SHA-256 `7f37d24fc14b3961fb58b403340532a947239a4a0bdce01f059485572d841c1c`.

Both are Scaleform CFX/SWF v8.

### Standard bottom subtitles

Retail entry point:

```text
fc_setSubtitles(text, speakerName, isPlayer)
```

The HUD receives **already resolved subtitle text**, not the localization row ID. Do not design runtime switching around the assumption that `fc_setSubtitles` receives a row key.

Standard field path:

```text
bc.subtitles.inside.tField
```

The TextField is multiline, word-wrapped, HTML-enabled, and read-only/no-select.

Retail performs its normal text write, then global `setTextSize(g_SpeachFontSize, tField)`, then position/background work. `setTextSize` applies a `TextFormat.size`, so secondary `<font size=...>` can be overwritten if applied too early. The successful proof restores the final `htmlText` **after** vanilla sizing.

### Overhead NPC bubbles

Retail entry point:

```text
fc_setBubbleText(bubbleId, bubbleText, speakerName, playerDistance)
```

Validated effective field path:

```text
cccursor.bubbles[Enum.BUBBLE_NAME_CORE + bubbleId].inside.tfText
```

The working patch restores generated HTML after vanilla processing and recalculates bubble geometry/background.

### Narrative/cinematic captions

Retail exposes:

```text
fc_setNarrativeSubtitles(text, layout, fadeIn)
fc_hideNarrativeSubtitles(fadeOut)
```

The narrative TextField is HTML-capable. One opening cutscene caption (`Несколько недель назад`) remained unstyled while later bottom subtitles in the same sequence were styled. This is strong evidence for a separate narrative path.

The exact final narrative TextField/member path and geometry/fade sequence are still unresolved under #54. Do not guess them from `fc_setSubtitles` or `fc_setBubbleText`.

### Runtime localization lookup

Retail HUD contains:

```text
TextExtension.translateString(key)
```

Private AVM1 inspection showed that it creates a temporary TextField and resolves a key through retail translation machinery. This is enabling evidence for #39, but **project-owned namespaced keys have not been live-proven in game**.

Before implementing the full runtime-language system, explicitly prove a generated key such as `@kcd2ds_<lang>_<row-id>` through `TextExtension.translateString` and prove a raw-key-safe fallback for missing keys.

### Menu.gfx

Vanilla `Menu.gfx` exposes generic page/value/choice functions including `fc_preparePage`, `fc_showPage`, `fc_addBasicButton`, `fc_addValueButton`, `fc_addChoicesButton`, `fc_addChoice`, `fc_getValue`/`fc_setValue`, and `fc_getChoice`/`fc_setChoice`.

This makes a native-looking in-game settings page plausible without KCSE/MCM, but navigation/events and persistence remain separate unsolved work.

No pure-retail persistence mechanism is proven. Do not introduce LuaDB/KCSE/ASI/`dinput8.dll` into the Xbox-first baseline. Session-only state with generator-defined defaults remains the safe initial contract unless a retail-safe persistence path is demonstrated.

## 5. Current HUD generation and patch architecture

CLI HUD mode is selected with:

```text
--subtitle-style hud
```

The normal/default tagged path remains separate and must not read or patch HUD assets.

For HUD mode the generator:

1. reads the user's installed retail HUD from `Data/IPL_GameData.pak` (`Libs/UI/hud.gfx`);
2. applies deterministic semantic AVM1 transforms;
3. builds a generated mod Data PAK containing `Libs/UI/hud.gfx`;
4. packages localization and Data PAK output under the project's mod directory;
5. installs through the existing staged/rollback-safe installer.

The project never ships a static proprietary `hud.gfx`.

### Data PAK compatibility lesson

A ZIP valid to Go/7-Zip can still be rejected by KCD2 CryPak. PR #44 fixed game-facing Data PAK entries to compatible Windows ZIP 1.0 (`10`) version fields, with raw binary header tests. After that change `kcd.log` showed the generated Data PAK opening successfully.

Do not regress those game-facing ZIP header fields. The already-working localization PAK writer was intentionally not changed by that fix.

### Foreign HUD conflicts

The installer fails closed if another installed mod provides `Libs/UI/hud.gfx` through a loose file or Data PAK. Preserve that behavior until an explicit, semantically validated effective-HUD composition strategy exists.

## 6. Current direct-HTML presentation path

The fixed-pair HUD path generates complete bilingual HTML in localization, then the HUD restores it after vanilla sizing.

The live-proven rc.10 default shape is conceptually:

```html
[MAIN] Primary text<br/><font color='#7FDBFF' size='24'><i>[SECONDARY] Secondary text</i></font>
```

There is deliberately **no `<p align='center'>` wrapper**.

Retail-proven through rc.10:

- ordinary bottom subtitles are styled;
- overhead NPC subtitles are styled;
- secondary color/italic/smaller size visibly render;
- dialogue choices also consume generated localization HTML;
- forced centering caused dialogue-choice horizontal displacement;
- removing forced centering restored normal dialogue-choice alignment.

This proves Scaleform `htmlText` styling in retail when restored after vanilla sizing.

### Post-rc.10 Stage 2: generator presentation configuration

PR #58 (`582bc87`) is merged and CI-accepted.

`generator.HUDPresentationConfig` now owns generation-time presentation:

- secondary color, default `#7FDBFF`;
- secondary size, default `24`;
- secondary italic, default `true`;
- language tags, default `true`.

Validation:

- color must be `#RRGGBB`;
- secondary size is conservatively bounded to `12..48` inclusive;
- explicit HUD presentation outside HUD mode fails closed;
- nil HUD config preserves the rc.10 defaults.

Only truly bilingual rows receive HUD presentation markup. Missing/identical/empty fallback behavior remains plain.

The `12..48` range is an implementation safety boundary, not a retail-proven claim that every value in the range has been visually accepted.

### Post-rc.10 Stage 3: native Windows GUI controls

PR #59 (`f681cb15`) is merged and CI-accepted.

The Win32 application now exposes:

- `Styled secondary subtitles`;
- `Show language tags`;
- secondary color;
- secondary size;
- secondary italic.

Compatibility contract:

- styled mode starts **off**, preserving the previous tagged GUI behavior unless the user opts in;
- when styled mode is enabled, the GUI constructs the same generator-owned `HUDPresentationConfig` used by generator tests;
- GUI does not contain a second formatting implementation;
- generator validation is reused before generation;
- dependent presentation controls are disabled while styled mode is off or the app is busy;
- autodetection, Browse, language selection, generate/regenerate, uninstall, and CLI paths remain separate from presentation formatting.

Automated acceptance for #59 was fully green: Format, Vet, Linux tests, Windows tests/build, native GUI smoke, and CLI smoke.

CI/release GUI smoke was also hardened: it now requires the real application-window title including a version, so the startup-error MessageBox cannot produce a false-positive smoke success.

**Retail acceptance for this GUI work is still pending.**

### Important architectural limitation

Embedding completed presentation HTML directly in dialogue localization rows leaks into other UI consumers of the same row, proven by styled dialogue choices.

Therefore direct localization HTML is acceptable as a retail proof, interim fixed-pair mode, and generation-time user-configurable mode. It must **not** become the final runtime-language transport.

The final #39 architecture should carry structured project data/keys and apply presentation inside subtitle render paths so dialogue-choice UI is not coupled to subtitle styling.

## 7. Failed experiments and lessons

Do not repeat these without a new hypothesis.

| RC / change | Result | Lesson |
| --- | --- | --- |
| rc.1 localization-only `<font>/<i>` | No visible style difference | Styling before vanilla HUD processing is insufficient for independent secondary presentation. |
| rc.2 hidden HTML-comment carrier + late wrapper | Only primary visible | Hidden comment transport is a poor diagnostic; it can disappear before rendering. |
| rc.3 plain `[KCD2DS1|...]` sentinel | Sentinel visible, no style | Localization transport worked; failure was downstream. Visible diagnostics are preferable for transport proofs. |
| rc.4 Data PAK ZIP fix | PAK opened, still no style | CryPak loading and AVM1 behavior are separate gates. |
| rc.5 direct HUD-active marker | Marker visible | Generated `hud.gfx` won resource resolution and executed. |
| rc.6 inline carrier parser | Sentinel still visible, no style | Parser/prelude approach was too complex for the proof stage. |
| rc.7 direct-HTML attempt | Generator failed on early `ActionReturn` | Semantic guards can be too strict; inspect real control flow first. |
| rc.8 standard direct HTML | Bottom subtitles styled | Save input HTML, let vanilla run, restore `htmlText` after sizing. |
| rc.9 bubble support | Bottom + overhead styled; narrative plain; choices shifted | Bubble path is separate; narrative is separate; localization HTML leaks to choices. |
| rc.10 remove forced centering | Dialogue-choice alignment normal | Do not override alignment without a demonstrated requirement. |

## 8. AVM1 patching lessons

- Locate target `DefineFunction2` structurally; do not depend on one absolute offset.
- Parse nested AVM1 bodies (`DefineFunction2`, `DefineFunction`, `With`, `Try`) so matching does not hit nested false positives.
- Validate semantic anchors and parameter/register contracts before mutation.
- Preserve unrelated SWF tags/actions byte-for-byte where possible.
- Use explicit idempotence markers for project-owned transforms.
- A retail function may use early guarded `ActionReturn` and still have a normal fall-through end path; analyze jumps before placing postludes.
- Respect `DefineFunction2` register binding.
- Prefer a simple proof that changes one known field over a complex parser/wrapper when diagnosing execution.
- Separate proof questions: localization transport, Data PAK loading, HUD resolution, AVM1 execution, lookup, and TextField styling should each be independently observable.

## 11. CI and release workflow

Normal PR acceptance expects:

- Format;
- Vet;
- Linux `go test ./...`;
- native Windows `go test ./...`;
- Windows build;
- native GUI smoke;
- CLI smoke;
- artifact upload.

Native GUI smoke now distinguishes the real versioned application window from the generic startup-error MessageBox.

Release-candidate branches are named:

```text
release-candidate/vX.Y.Z-rc.N
```

The create-event workflow repeats Format/Vet/Test/Windows gates, builds a versioned EXE and `SHA256SUMS.txt`, then publishes a GitHub prerelease.

A branch alone is **not** release evidence. Confirm the release workflow, published tag/release, and assets before telling the user an RC is available.
