# KCD2 Dual Subtitles — v0.3 development handoff

_Last updated: 2026-08-24. Repository baseline: `main` at `b54e8e7828f20cb6b452ca636e5b7aa76a647db7` after PR #56._

This document is the continuity source for future development sessions. Read it together with issues #39, #54, and #55 before changing the v0.3 path. It records what has been proven in the retail Xbox / Microsoft Store build, what was learned from private analysis of the user's installed game assets, which experiments failed, and which assumptions must not be repeated.

## 1. Project rules that must be preserved

- Plan each implementation slice before changing production code.
- Keep `main` releasable; production changes go through a branch and PR.
- GitHub Actions is the only automated acceptance source. Local builds/tests may be used for private editing/debugging, but are not merge/release evidence.
- Prefer small coherent PRs and explicit live gates over large speculative rewrites.
- Keep the project dependency-light; use the Go standard library where practical.
- Keep one Windows executable; the native Win32 GUI and CLI share the same application/generator core.
- Never modify original game files.
- Never commit or redistribute proprietary KCD2 localization/GFX assets. Real game files may be inspected privately for compatibility evidence only; CI uses synthetic fixtures.
- Unknown/malformed game UI structures fail closed rather than producing a possibly broken HUD.
- Do not advise users to disable Defender/SmartScreen. The executable is currently unsigned; release artifacts are produced by GitHub Actions with checksums.

## 3. Retail environment and localization evidence

Validated target remains KCD2 1.5.6 Xbox / Microsoft Store PC.

Private analysis of the installed English/Russian dialogue localization established:

- 177,930 dialogue rows in each language;
- identical ID sets and ordering;
- no duplicate IDs;
- 11 XML files in each language PAK, with `text_ui_dialog.xml` as the dialogue source used by this project;
- 30 rows contain actual embedded newlines;
- 4 displayed dialogue rows per language contain `<br/>`;
- no `<font>` markup was observed in translated dialogue text.

RU-main / EN-secondary comparison from the validated files:

- processed: 177,930;
- bilingual: 170,478;
- identical: 7,343;
- missing secondary: 0;
- main-empty fallback: 0;
- secondary-empty fallback: 109;
- secondary-only: 0.

The generator must continue preserving missing/identical/empty fallbacks rather than blindly styling every row.

## 4. Private retail GFX findings

Do not commit these assets or derived full binaries.

Validated hashes:

- `hud.gfx`: SHA-256 `85303baaeaa925ae051fe49626f15e638642908599886168682a16e402a065cd`;
- `Menu.gfx`: SHA-256 `7f37d24fc14b3961fb58b403340532a947239a4a0bdce01f059485572d841c1c`.

Both are Scaleform CFX/SWF v8.

### Standard bottom subtitles

Retail entry point:

```text
fc_setSubtitles(text, speakerName, isPlayer)
```

The HUD receives **already resolved subtitle text**, not the localization row ID. Do not design runtime switching around the assumption that `fc_setSubtitles` receives a row key.

Standard field path:

```text
bc.subtitles.inside.tField
```

The TextField is multiline, word-wrapped, HTML-enabled, and read-only/no-select.

Relevant retail flow:

- vanilla builds speaker-name markup when enabled;
- `TextExtension.setText(...)` writes through `htmlText` when formatting is involved;
- vanilla then calls global `setTextSize(g_SpeachFontSize, tField)`;
- then `updateSubtitlePosition()`;
- then `setSubtitlesBackground()`.

`setTextSize` creates a `TextFormat`, sets only `size`, and calls `setTextFormat`. This is why a secondary inline `<font size=...>` can be overwritten if applied before the vanilla size pass. The successful proof applies the final `htmlText` **after** vanilla processing.

### Overhead NPC bubbles

Retail entry point:

```text
fc_setBubbleText(bubbleId, bubbleText, speakerName, playerDistance)
```

Validated effective field path:

```text
cccursor.bubbles[Enum.BUBBLE_NAME_CORE + bubbleId].inside.tfText
```

Vanilla also performs text sizing/background work. The working patch restores generated HTML after vanilla processing and recalculates bubble geometry/background.

### Narrative/cinematic captions

Retail exposes:

```text
fc_setNarrativeSubtitles(text, layout, fadeIn)
fc_hideNarrativeSubtitles(fadeOut)
```

The narrative TextField is HTML-capable. One opening cutscene caption (`Несколько недель назад`) remained unstyled while later bottom subtitles in the same sequence were styled. This strongly indicates the separate narrative path. Exact final member/geometry sequence still needs to be finished under #54; do not guess it from the standard subtitle path.

### Runtime localization lookup

Retail HUD contains:

```text
TextExtension.translateString(key)
```

Private AVM1 inspection showed it creates a temporary TextField and resolves the key through the retail translation machinery. This is the key enabling evidence for the future #39 architecture, but **custom project-owned namespaced keys have not yet been live-proven in game**.

Next runtime-language proof should explicitly verify that a generated key such as `@kcd2ds_<lang>_<row-id>` resolves through `TextExtension.translateString` before building the full universal-language system.

### Menu.gfx

Vanilla `Menu.gfx` exposes generic functions including:

- `fc_clearAll()`;
- `fc_preparePage(...)`;
- `fc_showPage()`;
- `fc_addBasicButton(...)`;
- `fc_addValueButton(...)`;
- `fc_addChoicesButton(...)`;
- `fc_addChoice(...)`;
- `fc_getValue(...)` / `fc_setValue(...)`;
- `fc_getChoice(...)` / `fc_setChoice(...)`;
- `fc_setDisable(...)`;
- `fc_selectButton(...)`;
- `fc_isSomeButtonChanged()`.

These are sufficient evidence that a native-looking in-game settings page is plausible without KCSE/MCM. Navigation/events and persistence remain separate unsolved work.

No pure-retail persistence mechanism has been proven. Do not introduce LuaDB/KCSE/ASI/`dinput8.dll` into the Xbox-first baseline. Session-only runtime state with generator-defined defaults remains the safe initial contract unless retail-safe persistence is demonstrated.

## 5. Current HUD generation/patch architecture

The experimental style is explicitly selected as:

```text
--subtitle-style hud
```

The normal/default tagged path remains separate and must not read or patch HUD assets.

For HUD mode the generator:

1. reads the user's installed retail HUD from `Data/IPL_GameData.pak` (`Libs/UI/hud.gfx`);
2. applies deterministic semantic AVM1 transforms;
3. builds a generated mod Data PAK containing `Libs/UI/hud.gfx`;
4. packages the localization patch and Data PAK under the project's own mod directory;
5. installs through the existing staged/rollback-safe installer.

The project never ships a static proprietary `hud.gfx`.

### Data PAK compatibility lesson

A generated ZIP can be valid to Go/7-Zip and still be rejected by KCD2 CryPak.

The first HUD Data PAK used `archive/zip.CreateRaw` without explicit ZIP version fields, resulting in version fields unsuitable for CryPak. The game found the `*.pak` but did not report it as opened.

PR #44 fixed the game-facing Data PAK to use compatible Windows ZIP 1.0 (`10`) version fields for stored entries, with raw binary header tests. After this change `kcd.log` showed the expected successful open line for `kcd_dual_subtitles.pak`.

Do not regress these game-facing ZIP header fields. The already-working localization PAK writer contract was deliberately not changed as part of that fix.

### Foreign HUD conflicts

The installer currently fails closed if another installed mod provides `Libs/UI/hud.gfx` through a loose file or Data PAK. It does not silently overwrite another HUD mod. Preserve this until an explicit, semantically validated effective-HUD composition strategy is implemented.

## 6. Successful current direct-HTML proof

Current fixed-pair HUD HTML is generated in localization, then the HUD restores it after vanilla sizing.

After PR #56 / rc.10 the generated bilingual content conceptually is:

```html
[MAIN] Primary text<br/><font color='#7FDBFF' size='24'><i>[SECONDARY] Secondary text</i></font>
```

There is deliberately **no `<p align='center'>` wrapper**.

Current proof defaults:

- secondary color: `#7FDBFF`;
- secondary size: `24`;
- secondary italic: true;
- language tags: present.

These values are currently generation-time behavior, not runtime settings.

### Retail-proven results

By rc.9/rc.10 the user confirmed:

- normal bottom subtitles are styled;
- overhead NPC subtitles are styled;
- secondary color/italic/smaller size visibly render in retail;
- dialogue choices also consume the generated HTML;
- the forced `<p align='center'>` caused horizontal displacement in dialogue choices;
- rc.10 removed the forced centering and dialogue-choice alignment became normal.

This confirms that Scaleform `htmlText` styling works in the real retail HUD when applied after vanilla sizing.

### Important architectural limitation

Embedding completed presentation HTML directly in dialogue localization rows leaks into **other UI consumers of the same row**, proven by styled dialogue choices.

Therefore direct localization HTML is acceptable as:

- a retail proof;
- an interim fixed-pair mode;
- a generation-time user-configurable mode.

It should **not** become the final runtime-language transport. The final #39 architecture should carry structured project data/keys and apply presentation only inside subtitle render paths, so dialogue-choice UI is not coupled to subtitle styling.

## 7. Failed experiments and what they taught us

Do not repeat these without a new hypothesis.

| RC / change | Result | Lesson |
| --- | --- | --- |
| `v0.3.0-rc.1` localization-only `<font>/<i>` | No visible style difference | Styling before vanilla HUD processing is not sufficient for independent secondary presentation; vanilla sizing/render flow can overwrite or neutralize it. |
| rc.2 hidden HTML-comment carrier + late wrapper | Only primary visible | HTML comment carrier was a poor diagnostic because it could disappear before/inside rendering; wrapper execution also remained ambiguous. |
| rc.3 plain `[KCD2DS1|...]` sentinel | Sentinel visibly reached the screen; no style | Localization transport definitely worked; failure was downstream. Plain visible diagnostics are preferable when proving transport. |
| rc.4 Data PAK ZIP fix | PAK opened, still no style | CryPak compatibility and AVM1 behavior are separate gates; prove loading first. |
| rc.5 direct `[KCD2DS HUD ACTIVE]` mutation in retail `fc_setSubtitles` | Marker visible | Our generated `hud.gfx` definitely won resource resolution and executed. This ruled out load-order ambiguity. |
| rc.6 inline carrier parser | Sentinel still visible, no style | The parser/prelude approach was too complex/fragile for the next proof; simplify before adding runtime logic. |
| rc.7 direct-HTML attempt | Generator failed closed on an early `ActionReturn` | Semantic guards can be too strict. Inspect real control flow before declaring any `ActionReturn` incompatible. |
| rc.8 standard direct HTML | Bottom subtitles styled | Save input HTML in a free register, let vanilla run, then restore via `htmlText` after sizing. This is the proven standard path. |
| rc.9 bubble support | Bottom + overhead subtitles styled; narrative caption still plain; choices shifted | Bubble path is separate and now proven. Narrative is separate. Localization HTML leaks to choices. |
| rc.10 remove forced centering | Dialogue-choice alignment normal | Never override alignment without a demonstrated requirement; consumers of the same localization row have their own layout contract. |

## 8. AVM1 patching lessons

- Locate target `DefineFunction2` structurally; do not depend on one absolute offset.
- Parse nested AVM1 bodies (`DefineFunction2`, `DefineFunction`, `With`, `Try`) so target matching does not find nested false positives.
- Validate semantic anchors and parameter/register contracts before mutation.
- Preserve unrelated SWF tags/actions byte-for-byte where possible.
- Use explicit idempotence markers for project-owned transforms.
- A retail function may use early guarded `ActionReturn` and still have a normal fall-through end path. Analyze jumps before deciding where postludes belong.
- Respect `DefineFunction2` register binding. A parameter assigned to a register must be manipulated through that register rather than assumed to remain safely addressable by name.
- Prefer a simple proof that changes one known field over a complex parser/wrapper when diagnosing whether a layer executes.
- Separate proof questions: localization transport, Data PAK loading, HUD resource resolution, AVM1 execution, and TextField styling should each be independently observable.

## 9. Active issues and exact remaining work

### #55 — subtitle presentation options and Windows GUI controls

Stage 1 is complete and live-accepted in rc.10: forced centering removed, dialogue-choice alignment restored.

Next immediate work:

1. introduce a generator-owned presentation configuration with stable defaults;
2. support at least secondary color, size, italic, and language-tags on/off;
3. validate color as `#RRGGBB` and size within a conservative bounded range;

5. expose the same configuration through the native Windows GUI;
6. GUI must not implement formatting itself;
7. when styled mode is disabled, preserve the existing tagged generation path;

The user explicitly wants the ability to disable language tags because visual differentiation makes `[RU]` / `[EN]` less necessary.

Current GUI limitation: `application.Service.GenerateAndInstall(...)` does not pass `SubtitleStyleHUD`; normal GUI generation still follows the legacy/default tagged path. Do not mistake the CLI HUD proof for GUI integration.

## 11. CI/release workflow

Normal PR acceptance expects:

- Format;
- Vet;
- Linux `go test ./...`;
- native Windows `go test ./...`;
- Windows build;
- native GUI smoke;
- CLI smoke;
- artifact upload.

Release-candidate branches are named:

```text
release-candidate/vX.Y.Z-rc.N
```

The create-event workflow repeats Format/Vet/Test/Windows gates, builds a versioned EXE and `SHA256SUMS.txt`, then publishes a GitHub prerelease. A branch alone is not release evidence; confirm the actual tag/release/assets before telling the user it is published.
